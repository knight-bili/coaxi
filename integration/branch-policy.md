# V1.0.0 单分支开发约定

客户于 2026-10-18 明确要求，融合项目的唯一开发分支为 `develop/V1.0.0`，对应远程 `origin/develop/V1.0.0`。所有一期 I00–I12 与 BUF 的设计、编码、整改、测试和后续缺陷修复都在此分支累计，不再按阶段创建开发分支。

## 阶段、版本与验证

- I00–I12 继续是完整计划与工程验证的阶段，不改变 81 个来源功能簇、48 个工作包和 324 个正式场景。
- 阶段候选仍以 `fusion-iXX-rc.N` 和冻结提交 SHA 记录；阶段候选不是分支，也不自动创建发布标签或 Release。
- 多次中文本地提交，阶段编码与自审集齐后集中验证、少量推送；必要的安全、迁移或公共契约检查沿原规则执行。
- 普通同步不手动触发昂贵 Actions；阶段候选按涉及的平台选择工作流。等待远程结果时继续独立工作。
- 当前仓库仍以 `main` 为默认分支，统一开发分支跟踪 `origin/develop/V1.0.0`；Git 推送目标固定为本项目 `origin`，不得误推供体 `upstream`。

## main 与客户验收

`main` 不在归并操作中前移。只有 I12 必需研发、工程验证及客户真实软件使用验收全部通过，且客户再次明确指令后，才允许将 `develop/V1.0.0` 合入 `main`。不得自动合入、启用自动合并或正式发布；阶段结束、测试通过或普通“继续开发”不等于合入授权。

## 旧分支与未完成改动

旧阶段分支的全部提交必须先核对已被统一分支包含，再保存 Git bundle 与分支 SHA 清单，最后退役本地及远程旧分支。旧草稿 PR 关闭但不合并，历史提交和审查记录保留。

未完成且检查未通过的工作单独保存为可恢复的 stash 和逐文件核对过的压缩包；它们不因分支归并而丢失，也不被标记为完成。恢复后在统一分支继续修复、验证和提交，不恢复旧阶段分支作为开发线。

分支归并期间曾按客户要求暂停功能开发。客户于 2026-10-18 明确恢复开发；后续全部工作在统一开发分支继续。应用目标的暂停/续跑状态另行如实记录，不影响本轮已授权的研发。
