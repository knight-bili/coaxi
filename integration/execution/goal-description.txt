【分工与验收】Codex 负责设计细化、架构、编码、自审、代码审查、测试、构建、集成、GitHub 仓库与 PR 管理、阶段收口和修复。I12 完成前，用户只审核方案，以及提供 Codex 确实无法自行解决的环境、身份、预算、设备等外部条件，不承担技术测试、PR 审查、测试报告审核或逐阶段软件验收。已确认方案直接实施，普通实现选择和修复自行处理；需要改变产品方向、用户行为或模型输入等已定方案时，先提供易读的完整方案审核。

“客户验收”只指 I12 必需研发和工程验证完成后，用户取得可运行的完整软件，以真实用户身份使用并反馈是否满足需求。324个技术场景由 Codex 执行、记录证据并修复问题，不要求用户逐条跑测试，也不把代码、报告或 PR 代替软件交付。用户使用反馈引出的缺陷仍由 Codex 修复和回归。

I00–I12 内部统一称“研发实现”和“工程验证”，由 Codex 自行负责。准确区分“开发中、代码完成、工程验证中、工程验证通过、待环境验证”；不再将“等待客户验收”列为阶段收口条件或推进障碍。缺外部条件时保留未验证项，继续独立工作；最终 MVP 必须补齐所有必需实现和验证，不能通过改名、跳过或延期宣称完成。

【阶段推进】保持既定阶段范围与依赖，每阶段维护有限剩余清单、完成条件、验证方式、预计剩余工作和下一动作。不要把后续阶段的全部能力或最终产品验证无区别地压入当前阶段，也不得为进入下一阶段遗漏必需功能；新发现的缺陷按所属阶段和实际影响处理。当前继续 I03 的已确认私聊材料 r1 剩余上传、源内容变化检查、真实文件链路、迁入与孤立恢复，以及既定 Mission/Task/Diff 引用、文件节点、临时终端、冷启动和阶段集成；保留 I02 剩余项。等待阶段结果或外部条件时推进可独立的后续工作。

【提交与验证频率】多次本地 commit、阶段集中验证、少量 push。每个小功能、缺陷或调整先编码、自审并完成适当低成本检查，再中文本地提交；未编译、未运行项登记待验，不逐切片默认全量编译、全工作区回归、推送或触发 Actions。复用绑定准确源码的既有证据，避免重复检查和长篇重复报告。
